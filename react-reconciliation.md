# Reconciliation у React — покрокове пояснення для новачка

> Мета цього файлу: пояснити простими словами, що відбувається "під капотом" React
> від моменту, коли ми змінили стейт (`setState` / `useState`), і до моменту,
> коли користувач бачить оновлення на екрані (реальний DOM).

---

## Головна ідея одним реченням

React **не перемальовує всю сторінку** при кожній зміні. Замість цього він створює
нову "чернетку" інтерфейсу в пам'яті, **порівнює її зі старою** і змінює в реальному
DOM **тільки те, що дійсно змінилося**. Цей процес порівняння і називається
**reconciliation** (узгодження / звірка).

---

## Ключові поняття (словничок)

- **Реальний DOM (Real DOM)** — те, що бачить браузер і користувач. Змінювати його "дорого" (повільно).
- **Віртуальний DOM (Virtual DOM)** — легка копія DOM у вигляді JS-об'єктів. Змінювати її "дешево" (швидко).
- **Fiber** — внутрішня структура React (з версії 16), кожен елемент інтерфейсу має свій "fiber-вузол". Саме fiber робить оновлення переривчастим і пріоритетним.
- **Reconciliation** — процес порівняння нового віртуального дерева зі старим.
- **Diffing** — сам алгоритм пошуку різниці між деревами.
- **Commit** — момент, коли знайдені зміни реально застосовуються до DOM.

---

## Аналогія для новачка

Уяви, що ти редактор газети.

1. У тебе вже є **надрукована сторінка** (реальний DOM).
2. Тобі приносять **нову версію тексту** (новий віртуальний DOM).
3. Ти не передруковуєш всю сторінку заново. Ти береш маркер і **порівнюєш два тексти** (reconciliation),
   позначаючи лише ті абзаци, що змінилися.
4. Потім друкар змінює **тільки ці абзаци** на реальній сторінці (commit у DOM).

Це рівно те, що робить React.

---

## Покроковий процес: від `setState` до реального DOM

### Крок 1. Зміна стейту (тригер)

Все починається зі зміни даних. Наприклад:

```jsx
const [count, setCount] = useState(0);

// користувач натиснув кнопку:
setCount(count + 1);
```

Коли ми викликаємо `setCount` (або `this.setState`), React **не оновлює DOM миттєво**.
Він лише позначає компонент як "брудний" (dirty) — тобто такий, що потребує повторного рендеру,
і ставить оновлення в чергу.

> 💡 Важливо для новачка: `setState` **асинхронний** у контексті обробки подій.
> React може згрупувати (**batching**) кілька змін стейту в один рендер заради швидкодії.

---

### Крок 2. Render phase (фаза рендеру) — створення нового Virtual DOM

React заново викликає функцію компонента (або `render()` у класовому компоненті)
і всіх його дочірніх компонентів, які залежать від зміненого стейту.

Результат — **нове віртуальне дерево** (набір JS-об'єктів, які описують, як має виглядати UI).

```jsx
// JSX
<div className="counter">
  <p>Лічильник: {count}</p>
</div>

// перетворюється на приблизно такий об'єкт (Virtual DOM):
{
  type: 'div',
  props: { className: 'counter' },
  children: [
    { type: 'p', props: {}, children: ['Лічильник: 1'] }
  ]
}
```

> На цьому етапі **реальний DOM ще не чіпається**. Це все ще "чернетка" в пам'яті.
> Ця фаза може бути перервана React-ом (interruptible), якщо з'явиться важливіше завдання.

---

### Крок 3. Reconciliation + Diffing (серце процесу)

Тепер React має **два дерева**:
- **старе** (те, що було намальовано раніше);
- **нове** (щойно створене в Кроці 2).

React порівнює їх вузол за вузлом і шукає різницю. Щоб робити це швидко,
React використовує **евристики (спрощені правила)**, бо повне порівняння двох дерев
було б занадто повільним:

**Правило 1. Різний тип елемента → повна заміна.**
Якщо був `<div>`, а став `<span>` — React не намагається їх зіставити,
а просто видаляє старий вузол разом з дітьми і створює новий.

```jsx
// було
<div>Привіт</div>
// стало
<span>Привіт</span>
// → React знищує div і будує span з нуля
```

**Правило 2. Той самий тип елемента → оновлюються тільки змінені атрибути.**

```jsx
// було
<p className="text">Лічильник: 0</p>
// стало
<p className="text">Лічильник: 1</p>
// → React залишає той самий <p>, змінює лише текст всередині
```

**Правило 3. Списки порівнюються за `key`.**
Саме тому в списках потрібен унікальний і стабільний `key` — він каже React,
який елемент є яким, щоб не перестворювати весь список.

```jsx
{events.map((event) => (
  <EventCard key={event.id} {...event} />
))}
```

> ❌ Не використовуй `index` масиву як `key`, якщо список може змінювати порядок,
> сортуватися чи фільтруватися — це ламає reconciliation і призводить до багів та зайвих ререндерів.

Підсумок цього кроку: React формує список **мінімальних змін** (effect list) —
"що саме треба змінити в реальному DOM".

---

### Крок 4. Commit phase (фаза застосування)

Тепер React бере список змін з Кроку 3 і **застосовує їх до реального DOM** одним махом:
- додає нові вузли;
- видаляє непотрібні;
- оновлює атрибути та текст там, де це потрібно.

Ця фаза **не переривається** (synchronous) — React робить усі зміни за один раз,
щоб користувач не побачив "напівоновлений" інтерфейс.

Саме тут реальний DOM нарешті змінюється, і браузер перемальовує (repaint) екран.

---

### Крок 5. Ефекти (після оновлення DOM)

Після того як DOM оновлено, React запускає ефекти:
- `useLayoutEffect` — синхронно, одразу після зміни DOM, але до того, як браузер намалює кадр.
- `useEffect` — асинхронно, вже після того, як браузер намалював оновлення.

```jsx
useEffect(() => {
  console.log('DOM вже оновлено, count =', count);
}, [count]);
```

---

## Повна схема процесу

```
[setState / useState]
        │
        ▼
1. Стейт змінився → компонент позначено як "потребує оновлення"
        │
        ▼
2. RENDER PHASE: React викликає компонент → створює НОВИЙ Virtual DOM
        │
        ▼
3. RECONCILIATION (DIFFING): порівняння нового дерева зі старим
     • різний тип       → замінити вузол повністю
     • той самий тип    → оновити лише змінені пропси/текст
     • списки           → зіставити за key
     → формується список мінімальних змін
        │
        ▼
4. COMMIT PHASE: зміни застосовуються до РЕАЛЬНОГО DOM
        │
        ▼
5. Браузер перемальовує екран → запускаються useLayoutEffect / useEffect
```

---

## Часті питання новачків

**Чому React швидкий, якщо він рендерить компонент заново?**
Бо "рендер" створює лише легкі JS-об'єкти (віртуальний DOM), а не чіпає повільний реальний DOM.
Реальний DOM змінюється тільки в Кроці 4 і тільки в тих місцях, де є різниця.

**`setState` одразу міняє DOM?**
Ні. Він лише планує оновлення. Реальний DOM зміниться пізніше, у commit phase.

**Навіщо потрібен `key`?**
Щоб під час reconciliation React зрозумів, який елемент списку якому відповідає,
і не перестворював елементи дарма.

**Що таке Fiber?**
Це нова архітектура React (з v16), яка дозволяє розбивати роботу рендеру на маленькі
частини, ставити їм пріоритети і за потреби переривати. Завдяки цьому інтерфейс
залишається чуйним навіть під час великих оновлень.

---

## Головне, що треба запам'ятати

1. Зміна стейту → **не** миттєва зміна DOM.
2. React будує **новий віртуальний DOM** в пам'яті.
3. **Reconciliation** порівнює новий і старий віртуальний DOM.
4. У **реальний DOM** потрапляють **лише реальні зміни**.
5. `key` та правильна структура компонентів роблять цей процес ефективним.
